# 9. Agents are integrated through ACP

- Status: Accepted
- Date: 2026-10-26

## Context and Problem Statement

The runtime needs to drive agents (prompt them, stream their output, see tool calls, answer permission requests, steer them, resume them) and expose sessions to UIs.

Two approaches:

1. Wrap Claude Code's interactive CLI and use its terminal UI and Remote Control.
2. Drive agents through a protocol.

## Considered Options

- Wrap the `claude` CLI and its terminal UI
- The Claude Agent SDK, directly
- The [Agent Client Protocol](https://agentclientprotocol.com) (ACP): an open JSON-RPC protocol between clients and agents, with Claude supported through [`claude-agent-acp`](https://github.com/agentclientprotocol/claude-agent-acp), which is built on the Agent SDK

## Decision Outcome

Chosen option: **ACP**.

The runtime is an ACP **client** towards each agent and an ACP **proxy** (an agent) towards UIs:

- **Endpoint:** one `/acp` WebSocket endpoint, the WebSocket mode of the Streamable HTTP & WebSocket transport RFD.
- **Session list and load:** `session/list` merges sessions across pods. `session/load` replays from the runtime's event log.
- **Capabilities:** the runtime copies the agent's `initialize` capabilities into its own initialize response and passes `_session/steering` through unchanged.
- **Several UIs at once:** every attached UI receives every update. Permission requests go to all of them and to the approval queue; the first answer wins and the others are cancelled.
- **No UI required.** Sessions never depend on a UI being attached. Everything goes into the event log, and permission requests land in the durable approval queue and trigger a notification. A turn waits only on a decision it genuinely needs, never on someone having a UI open.

Approvals within a session use ACP natively: `session/request_permission`, plus `elicitation/create` (Completed RFD) for editing fields, comments and picking a TTL. Anything that spans sessions (approval queue, board, grants, parked sessions) is runtime API, not ACP.

### Consequences

- Good: agent-agnostic. Codex, Gemini CLI, Copilot, goose and others speak ACP natively.
- Good: Claude Code features keep working through the adapter, including auto mode, hooks, settings and CLAUDE.md. The adapter maps the `auto` mode and loads user, project and local settings.
- Good: existing ACP clients that can connect to a remote endpoint, such as Ferngeist (Android), Agmente (iOS) and Panda (web), work as fallback chat views.
- Bad: Claude Code's terminal UI and Remote Control are not the primary interface, so we build our own UI ([ADR 18](0018-ui.md)). Escape hatch: a session driven through the SDK can still be opened in the terminal UI with `claude --resume <id>`, as long as nothing else is driving it at the same time.
- Bad: remote transport and steering are still RFDs or vendor extensions, so expect churn.
